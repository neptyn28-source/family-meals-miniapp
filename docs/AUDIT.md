## 1. Баги

### P0

**B1. Бюджет: остатки конвертов считаются по последним 80 операциям** — P0, M
`supabase/functions/family-budget/index.ts:9` (`state()`: `.order("created_at",{ascending:false}).limit(80)`, затем суммирование).
Как воспроизвести: сделать 81 расход по 1 ₽ из одного конверта. Остаток «вырастет» на 1 ₽, потому что старая операция выпала из выборки. При этом `envelope_adjust` и `envelope_archive` считают по всем строкам: сверка ставит неверную дельту, архив пишет «переведите остаток», хотя на экране 0.
Исправление: считать сумму в SQL (`sum()` по конверту, вьюха или RPC). Тест на 100+ операций.

**B2. Импорт меню без транзакции** — P0, M
`supabase/functions/ai-menu-api/index.ts:689-738`. Порядок такой: upsert блюд → delete и insert cook-blocks → delete и insert покупок → аудит → update недели.
Как воспроизвести: импорт, который падает в середине. Например, триггер `20261012_guard_shopping_retail_pack.sql:30` бросает исключение на фрукт в `pcs` (так в каталоге из репо, см. D3). Блюда уже перезаписаны, покупки удалены, клиент получил 500.
Исправление: перенести запись в одну Postgres-функцию (RPC) с транзакцией, сохранить формат JSON.

**B3. Сохранение «Вес и цели» теряет данные** — P0, S
`app-v2.js:618-651` вызывает через `Promise.all` два запроса: `profile.update` (`ai-menu-api/index.ts:531-536`) и `settings.update` (`family-api/index.ts:462-472`). Оба читают `family_settings.settings` и пишут его целиком.
Как воспроизвести: поменять вес и бюджет, нажать «Сохранить», открыть экран заново. Иногда откатывается одно из двух. Если упал один запрос, пользователь видит просто «Ошибка».
Исправление: вызывать по очереди или объединить в один серверный action с merge.

**B4. Бюджет: ошибки insert не проверяются** — P0, S
`family-budget/index.ts:11` (`expense`, `personal`, `transfer`). Клиент получает `ok:true`, а операция не записана. Деньги тихо «теряются».
Исправление: проверять `error` после каждого insert.

### Форматы ошибок сейчас

1. `{ok:false, error:"<код>", message}` — 401, `not_invited`, `invite_*`, `week_not_validated`.
2. `{ok:false, error:"<английская фраза>"}` — 400/404 в `family-api`.
3. `{ok:false, error:"<сырой текст исключения>"}` — 500 в `family-api` и `ai-menu-api`.
4. `{ok:false, error, message, issues[], shopping?}` — 422 `menu_validation`, `budget_exceeded`.
5. `{ok:false, error:"bad_text"|"server_error"}` — `home-wms-api`; `"Server error"` — `week-generate`; русский текст или сырой текст БД — `family-budget`.

Цель — общий хелпер `_shared/http.ts`: `{ok:false, error:"<понятный текст>", code:"<машинный код>", issues?}`. Клиент переводит по `code`.

## 5. План перехода `family-budget` на Telegram initData (без потери данных)

Связи сейчас: `fb_members(id, household_id, display_name, role, device_token_hash)`. На них ссылаются `fb_envelopes.owner_member_id`, `fb_operations.member_id`, `fb_income_events.member_id`. Семья хранится в `fb_households(id, name, invite_code)`.

1. **Миграция (только добавляет, идемпотентная):** `fb_members.telegram_user_id bigint null unique`, `fb_households.family_id uuid null`. Найти дубли `device_token_hash` и добавить уникальный индекс. Ничего не удалять.
2. **Двойная авторизация:** сначала `verifyInitData` из `_shared/telegram.ts` и поиск по `telegram_user_id`; если не найден — запасной вход по `x-device-token`.
3. **Привязка при первом открытии в Telegram:** валидный initData плюс валидный device token, `telegram_user_id` пуст. Тогда записываем id, если он не занят (иначе 409). Каждую привязку логировать.
4. **Восстановление:** участник из `family_members` той же семьи может занять «осиротевшего» `fb_member` своей роли — только после подтверждения вторым супругом.
5. **Новые семьи** создаются только через initData, приглашения одноразовые со сроком, как в `family-api`.
6. **Когда у всех `telegram_user_id` заполнен** — отключить device token, удалить `fbtoken` из `localStorage`, включить RLS на `fb_*`.

⚠️ Шаги 1–3 и особенно 6 меняют способ входа — **нужно согласие пользователя**.
